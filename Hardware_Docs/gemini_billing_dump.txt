4. Production API Architecture — Per-User Key Management

4.1 The Core Problem

When hundreds or thousands of ADAM units are deployed, you cannot embed a single DGEN API key in every ADAM's firmware. If one unit is hacked or the key leaks, every ADAM stops working. The solution is Ephemeral Tokens — Google's own recommended approach for exactly this scenario.

4.2 Ephemeral Tokens — Google's Recommended Multi-User Architecture

Ephemeral tokens are short-lived authentication credentials that DGEN's backend generates for each ADAM session. They are documented in the official Gemini API docs at ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens

How Ephemeral Tokens Work

Step

Actor

Action

1

ADAM Unit

Detects presence (RCWL-0516 radar) + wake word → prepares to start session

2

ADAM Unit → DGEN Server

Sends authentication request with device serial number + user token

3

DGEN Server

Verifies user identity and checks if user has valid credits/is authorised

4

DGEN Server → Google

Requests an ephemeral token using DGEN's master API key (stays server-side, never exposed)

5

Google → DGEN Server

Returns a short-lived token (valid: 1 min to start, 30 min session max)

6

DGEN Server → ADAM Unit

Sends ephemeral token to ADAM

7

ADAM Unit → Google

ADAM connects directly to Gemini Live API using the ephemeral token

8

Session ends

Token expires — useless even if extracted. Next session requires fresh token.

Security Properties of This Architecture

DGEN's master API key NEVER leaves the backend server

Each ephemeral token is single-use and expires in 30 minutes

If an ADAM unit is stolen and its token extracted, it becomes useless within 30 minutes

You can revoke access for any device by simply refusing to generate tokens for it

Each token can be locked to a specific model, configuration, and system prompt — users cannot change the model or bypass your system instructions

4.3 Code Skeleton — Backend Token Generator (Node.js)

// DGEN Backend — Ephemeral Token Generator (Express.js)

// POST /api/adam/token — called by ADAM unit at session start

const { GoogleGenAI } = require('@google/genai');

const client = new GoogleGenAI({ apiKey: process.env.DGEN_MASTER_KEY });

app.post('/api/adam/token', authenticateDevice, async (req, res) => {

  const { deviceId, userId } = req.body;

  // 1. Check user credit balance in Supabase

  const credits = await checkUserCredits(userId);

  if (credits <= 0) return res.status(402).json({ mode: 'lite' });

  // 2. Generate ephemeral token locked to ADAM's config

  const token = await client.authTokens.create({

    config: {

      uses: 1,

      expireTime: new Date(Date.now() + 30*60*1000).toISOString(),

      liveConnectConstraints: {

        model: 'gemini-3.1-flash-live-preview',

        config: { sessionResumption: {}, responseModalities: ['AUDIO'] }

      },

      httpOptions: { apiVersion: 'v1alpha' }

    }

  });

  // 3. Deduct from user credits (or track usage)

  await logSessionStart(userId, deviceId);

  res.json({ token: token.name, expiresAt: token.expireTime });

});

4.4 ADAM Pi Zero 2W — Session Startup Flow

The updated boot sequence for production ADAM units using ephemeral tokens:

Radar detects presence → Vosk detects wake word

Pi Zero 2W sends HTTPS POST to DGEN backend with device_id + stored user_token

Backend validates, checks credits, returns ephemeral token (or 'lite_mode' flag)

ADAM uses ephemeral token to open Gemini Live WebSocket session

Session runs up to 30 minutes (with resumption handles for reconnects within that window)

Session closes when user walks away (radar inactive for 30+ seconds)

Next session requires a fresh token request

4.5 Alternative: BYOK (Bring Your Own Key)

For technically inclined users or the Indian market where cost sensitivity is high, BYOK is a valid alternative to the centralized token approach:

User creates a Google account and gets their own free Gemini API key from aistudio.google.com

User enters the key once during ADAM first-time setup (via a local web UI on the Pi)

The key is stored encrypted in the Pi's local storage

ADAM uses the user's own key → DGEN pays zero API costs

User gets their own free tier quota: effectively unlimited for a single ADAM unit

ℹ  NOTE: BYOK is the recommended default for Version 1 of ADAM. It has zero AI infrastructure cost for DGEN and gives users the free tier. DGEN monetizes entirely on hardware margin at this stage. The centralized token architecture becomes relevant in Version 2 when DGEN charges for AI credits.

6. What Happens When a User Does Not Pay / Has No Credits

6.1 Core Principle — Never Brick the Robot

ADAM must remain a useful device regardless of whether the user has AI credits or a configured API key. This is critical for:

User satisfaction and product reviews

Smart home / IoT features which have nothing to do with AI costs

Indian consumer trust — they paid ₹14,999+ for hardware, it should do something

ℹ  NOTE: ADAM Lite Mode must feel like a deliberate product tier, not a broken state. Good fallback design makes the upgrade to full AI feel like a desirable enhancement, not a demand.

6.3 Upgrade Prompts — How ADAM Encourages Users to Get Credits

When in Lite Mode, ADAM should intelligently nudge users toward getting a key or buying credits, without being annoying:

Once per day: ADAM face shows a gentle 'thinking' animation and ADAM speaks a pre-recorded message like: "I can do a lot more if you set up my AI connection. Want to know how?"

When user tries to ask a question ADAM cannot answer in Lite Mode: ADAM says "I can answer that once you connect my brain — it takes two minutes to set up."

QR code displayed on TFT screen linking to DGEN setup page

DGEN app sends push notification (once per week): "ADAM is working in Lite Mode — unlock full AI for ₹599."

ℹ  NOTE: Nudges should be gentle, infrequent, and helpful — not aggressive upsell. ADAM's personality must stay consistent and friendly even in Lite Mode.

7.2 Free Tier Key Pooling Strategy (Phase 1)

For Phase 1, DGEN can create multiple Google accounts (one per team member) and pool their free tier keys. Route ADAM sessions round-robin across keys to distribute the 65K TPM limit.

5 free tier keys × 65K TPM = 325K TPM total

325K TPM / 14K tokens per active session = ~23 simultaneous active ADAM sessions

For 50 units where most users are not simultaneously active, this comfortably supports the fleet

Each key is under a different Google account — usage is free with standard data-training trade-off

⚠  WARNING: Operating multiple Google accounts for key pooling may be against Google's Terms of Service. Verify with Google's commercial team or simply launch with BYOK to avoid any ToS risk.
