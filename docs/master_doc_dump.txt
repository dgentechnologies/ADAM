3. System Architecture

ADAM's architecture has evolved from the working v32 prototype toward a unified custom-PCB production architecture.

Current system view

Body / Main Compute

Head / Real-time I/O

Cloud / Devices

Raspberry Pi Zero 2 W AI orchestration + memory Gemini Live + audio I/O Pan servo + UART

ESP32-S3 production target OV2640 camera ILI9341 TFT Touch + tilt servo

Gemini Live Web / smart-home tools Laptop agent Mobile / desktop UI

Production direction: consolidate head electronics onto a unified ESP32-S3 motherboard.

Current working prototype architecture (v32)

Body: Raspberry Pi Zero 2 W as the main compute/orchestration unit; audio I/O, Gemini Live session, memory, pan servo and body↔head communications.

Head: ESP32-CAM for camera capture, touch/gesture sensing and tilt servo control; Raspberry Pi Pico drives the ILI9341 face display.

Neck link: four wires — 5V, GND, TX and RX — over a wired UART path. Zero Wi-Fi is used for the vision link.

Production hardware direction

Body motherboard BOM 1: Raspberry Pi Zero 2 W integrated with discrete power, audio ADC, amplifier, servo protection and neck interface circuitry.

Head motherboard: ESP32-S3-WROOM-1-N16R8/N8R8 consolidating camera, TFT, touch, tilt servo and programming interfaces onto one PCB.

Advanced body option BOM 2: Raspberry Pi Compute Module 4 Lite carrier architecture for higher-performance computer vision/OpenCV and multi-threaded AI workloads.

Important: the v32 document describes the working assembled architecture, while the production BOM documents describe the next production PCB architecture. They are not identical hardware revisions.

Component

ADAM executes the selected function through its own Python/runtime integrations; Needle does not replace the executor.

Memory — route save, recall and related memory operations using explicit tool schemas.

Computer control — select narrowly defined actions for the connected laptop/PC rather than generating unrestricted commands.

Needle 3 deployment decision

Needle 3 is the current target because Cactus positions it specifically for mobile, wearables, robots, smart home and microcontroller-class devices. Its ladder allows the same model family to be built from 2 to 20 layers. For ADAM, 4-layer and 8-layer builds should be benchmarked on the Raspberry Pi Zero 2 W before the production depth is frozen.

Body Motherboard — BOM 1

Compute core: Raspberry Pi Zero 2 W.

2-layer or 4-layer FR4, 1.6 mm, 1 oz copper.

3.0 A primary input polyfuse and reverse-polarity protection.

2200 µF 16 V low-ESR input reservoir; dedicated 1000 µF servo-local reservoir.

PCM1808 24-bit / 96 kHz stereo I2S ADC with synchronous master-clock topology.

MAX98357A 3.2 W mono Class-D I2S amplifier.

921600-baud shielded UART neck interface to the head motherboard.

Head Motherboard — ESP32-S3

ESP32-S3-WROOM-1-N16R8 / N8R8; 240 MHz dual-core Xtensa LX7.

8 MB Octal PSRAM; 16 MB Flash recommended for production.

OV2640 2 MP camera via 24-pin FPC.

ILI9341 2.4-inch 320×240 display via high-speed DMA SPI.

TFT control deliberately moved to GPIO37/GPIO38; GPIO45/GPIO46/GPIO3 left isolated as documented strapping-risk mitigation.

Camera SCCB uses GPIO39/GPIO40; touch channels use GPIO1/GPIO2/GPIO4/GPIO14.

Production head uses a unified controller rather than the prototype's ESP32-CAM + Pico split.

Advanced Body Motherboard — BOM 2

Raspberry Pi CM4 Lite with 2 GB or 4 GB LPDDR4.

Dual Hirose DF40 100-pin board-to-board connectors.

4-layer FR4 carrier with controlled-impedance routing.

MicroSD storage, external dual-band antenna, nRPIBOOT recovery and GLOBAL_EN reset access.

Designed for higher-performance OpenCV, computer vision and multi-threaded AI workloads.

15. Engineering Architecture Notes

Function-calling architecture

Gemini Live is the conversational intelligence layer; Needle 3 is a specialised local model for selecting tools and filling typed arguments.

Needle 3 does not act as ADAM's general chat model. Its job is structured automation: request → tool selection → arguments → JSON call.

The tool set should remain narrow and explicit: one tool per action, user-facing names, clear argument formats and constraints.

For requests that need multiple actions, Needle 3 can emit multiple calls in order; unsupported requests can return an empty call list instead of inventing an action.

Needle 3 responses include a confidence value. ADAM's runtime should use this to distinguish automatic execution from confirmation-required actions.

Triggers can be used for intents that must reach a particular tool, while the final executor remains under ADAM's application control.

Structured extraction can support mobile notification parsing and other inputs where ADAM needs typed fields rather than free-form prose.

The initial ADAM deployment should benchmark Needle 3 at 4L and 8L on the actual Pi Zero 2 W.

Audio architecture

Production body BOMs define the Raspberry Pi/CM4 as I2S master.

PCM1808 ADC and MAX98357A amplifier are treated as synchronized I2S slaves.

The documented master-clock path uses GPCLK0 / GPIO4 at 12.288 MHz for a 48 kHz audio system.

Servo power has a dedicated protected branch to reduce brownout and motor-noise risk.

Head + wiring architecture

ESP32-S3 production design keeps GPIO45, GPIO46 and GPIO3 isolated from functional routing.

Camera SCCB uses GPIO39/GPIO40; TFT SPI uses GPIO35/GPIO36 with DC/CS on GPIO37/GPIO38 and reset on GPIO47.

Touch channels are mapped to GPIO1/GPIO2/GPIO4/GPIO14.

The neck interface is deliberately minimised to four electrical conductors; the moving head keeps camera/display/touch electronics local.

16. Privacy, API & Service Design Considerations

Production deployments should not expose a permanent shared Gemini API key directly to every unit.

The monetisation strategy identifies ephemeral-token architecture as the production direction for multi-user deployments.

The strategy notes a privacy trade-off associated with certain free-tier AI usage and calls for user consent where applicable.

User-facing settings should clearly explain AI connectivity, API-key/BYOK configuration, credit status and what functions work locally.

The product philosophy is to preserve local functionality when cloud AI is unavailable.

This document intentionally does not define final legal/privacy policy text. Those policies should be maintained separately and reviewed before commercial release.

18. Mobile App Architecture

Integrated mobile product architecture, setup, BLE provisioning and operating surfaces.

Product architecture

Monorepo: Turborepo + pnpm workspaces with apps/web, apps/api and apps/mobile-shell, plus shared UI, types and configuration packages.

Web layer: Next.js 15 App Router with static export for the Capacitor shell, allowing the same application surface to support browser preview and native mobile packaging.

Native shell: Capacitor targets Android and iOS; native plugins provide BLE, camera and secure-storage capabilities.

Shared contracts: strict TypeScript/Zod models cover authentication, device telemetry, Wi-Fi provisioning, setup state, memory, gallery, OTA, credits and preferences.

Backend: Fastify REST/WebSocket contract for authentication, device state, memory, gallery, OTA and credit services; routes and persistence layer remain implementation work.

13-stage first-run setup

Splash → Welcome → Sign-in → BLE device discovery → Device found/pairing validation → Wi-Fi selection → Wi-Fi password → Connecting/handshake → Name device → Founder Edition reveal → AI Brain selection → BYOK/Credits/Lite configuration → Camera permission and owner face capture.

The setup flow supports Google Sign-In or Email OTP, scans for ADAM-XXXX BLE advertisements, filters 2.4 GHz Wi-Fi networks, shows connection progress and stores setup state locally.

Founder Edition units #001–#010 receive a dedicated recognition/reveal screen during onboarding.

BLE provisioning and connectivity

ADAM's ESP32-S3 is the Bluetooth LE endpoint used for mobile provisioning and nearby mobile communication.

The Raspberry Pi's Bluetooth is intentionally turned off in the ADAM architecture; BLE responsibilities remain on the ESP32 side.

The mobile app discovers an ADAM-XXXX advertisement, validates the device/serial, then uses BLE to transfer provisioning data and establish the initial setup relationship.

After Wi-Fi provisioning, local-network discovery can use mDNS/Zeroconf to locate adam.local. A future production bridge can maintain a WebSocket for live telemetry.

Connectivity principle: Mobile → BLE → ESP32-S3 for provisioning/nearby control. ADAM's Pi → Wi-Fi/Ethernet-network services for normal cloud/local operation. Pi Bluetooth remains disabled.

20. AI Access, Desktop App & Cross-Device Experience

Three AI setup choices

Mode

Description

BYOK

User supplies their own Gemini API key. AI usage is billed directly to the user's chosen provider account.

Dgen Managed Credits

User purchases Dgen-managed AI credits, providing a simpler setup plus Dgen-managed privacy/service features and usage accounting.

Lite Mode

No Dgen-managed AI service required. Needle 3 handles supported local function-calling/automation; full cloud conversation is unavailable.

AI responsibility split

Gemini handles the natural conversation and multimodal conversational intelligence.

Needle 3 handles local function calling: selecting the appropriate tool, filling typed arguments, supporting ordered multi-call requests and exposing confidence for routing.

ADAM's application runtime remains the executor. Needle 3 does not receive unrestricted control of the robot; the runtime decides which permitted tools can actually execute.

Mobile configuration determines which AI access mode is active; the device/runtime applies the corresponding service policy.

Desktop companion app

A background/tray application connects the user's laptop/PC to ADAM and provides the computer-control bridge.

Vibe-coding integration can surface Claude Code or Codex status events to ADAM, including input required, task completed, task stopped and similar states.

The desktop bridge supports assistive workflows such as preparing text and sending it to the connected computer's clipboard, helping draft mail and performing approved computer actions.

Paired laptops are represented in the mobile app.

Cross-device model: Mobile app = setup, account, AI access, memory, gallery and device management. Desktop app = computer/agent bridge and coding status. ADAM = physical interaction, conversation, sensors and local execution. BLE is anchored on the ESP32-S3, while the Pi remains the main AI/runtime computer.

21. User Setup, AI Access Modes & Privacy Architecture

First-time setup

Power on ADAM → mobile app discovers/pairs with ADAM over BLE → user signs in or creates the Dgen account → device is associated with the user's account.

User chooses an AI access mode. The choice can be changed later through the mobile/desktop settings.

User grants only the permissions needed for the selected features, including notification access and computer permissions required by the desktop agent.

Privacy and data boundaries

Presence radar processing is local to ADAM.

BLE provisioning and phone communication are local radio links between the mobile app and the ESP32-S3.

Notification reading is opt-in and controlled by the mobile app.

BYOK keeps Gemini authentication under the user's own Google/Gemini account.

Dgen-managed credits use the Dgen service layer for entitlement/authentication and Gemini session access; the production architecture should use short-lived credentials rather than a permanent Dgen master key in each device.

Lite Mode is designed to operate without Dgen AI calls.
